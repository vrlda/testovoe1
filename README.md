# Funnel Runtime

Воронки из JSON-конфига с версиями, откатом, A/B-тестом, своими событиями и дашбордом. React + Node.js + SQLite, всё на TypeScript.

- Воронка: https://test.vrld.cc/?new=1
- Админка: https://test.vrld.cc/admin (токен передан отдельно)
- Репозиторий: https://github.com/vrlda/testovoe1

## Запуск

Нужен Node.js 24+ (используется встроенный `node:sqlite`).

```bash
npm ci
ADMIN_TOKEN=change-this npm run dev
```

Воронка — http://localhost:5173, админка — http://localhost:5173/admin, API — порт 3001.

Прод-сборка, фронт и API на одном порту:

```bash
npm run build
ADMIN_TOKEN=long-random-secret PORT=3001 npm start
```

База `data/funnel.sqlite` создаётся сама. При первом старте публикуется v1, v2 и v3 загружаются через админку.

```bash
npm test                 # 31 тест
npm run generate         # 120 синтетических сессий в активную версию
DB_PATH=/tmp/demo.sqlite npm run generate   # то же, в отдельную базу
```

## Как устроено

Конфиги из задания лежат в `configs/` без изменений. Сервер приводит их к внутреннему виду: шаги варианта, условия `visibleWhen`, правила результата, список разрешённых событий. Фронт ничего не знает про конкретные экраны — он рисует пять типов шагов (info, single, multi, number, result) по тому, что вернул сервер.

Состояние сессии хранится на сервере: ответы, история для Back, текущий шаг. Клиент держит в `localStorage` только ID сессии и черновик ввода, поэтому refresh и повторное открытие возвращают на тот же шаг. Если ответ на шаге меняет ветку, ответы со скрытых шагов удаляются и больше не влияют на результат. Прогресс считает только видимые вопросы, без intro и результата.

Если два запроса пришли на один шаг (двойной клик, повтор после таймаута), второй получает 409, и клиент перечитывает состояние.

### Версии и откат

Каждая публикация — новая неизменяемая строка в `configs`. Сессия запоминает версию и вариант при создании и дальше работает только с ними, поэтому публикация и откат затрагивают только новые сессии.

Откат ведёт на версию, которая была активна до текущей, а не на номер меньше. Для этого есть журнал `activations`: публикация добавляет запись, откат помечает текущую запись как откаченную. Изменение долей A/B тоже создаёт версию, и откат корректно через неё проходит. Таблица создаётся на старте через `CREATE TABLE IF NOT EXISTS`, ручной миграции нет.

У версии два номера: внутренний (порядок публикаций) и `version` из JSON. На стенде v3 опубликован дважды (до и после проверочного отката), поэтому активна внутренняя 4 с исходным v3.

## A/B-тест

Вариант назначает сервер по весам из конфига и сохраняет в сессии. Для ручной проверки: `/?variant=A&new=1` или `/?variant=B&new=1`. Такие сессии живут в `sessionStorage`, чтобы вкладки A и B не мешали друг другу.

**Что отличается в B.** Вопрос о формате работы идёт первым, intro сформулирован через проблему («Is your team losing time…»), другие заголовки результатов и текст CTA. В v3 из B вдобавок убран `tool_count`.

**Гипотеза.** Если начать с проблемы и простого вопроса о формате работы, больше людей дойдут до рекомендации.

**Основная метрика** — доля начатых сессий, дошедших до результата. Заголовки результатов её изменить не могут: их видят только те, кто уже дошёл. Они проверяются вторичной метрикой — CTR кнопки среди сессий с результатом.

**Оговорки.** B меняет сразу несколько вещей, поэтому тест отвечает на вопрос «B лучше A?», а не «что именно сработало». В v3 к этому добавился более короткий путь, так что результаты v3 нельзя складывать с v1/v2 — дашборд показывает их отдельно по версиям. Рядом с разницей A/B выводится 95% доверительный интервал. Для ориентира: чтобы увидеть разницу в 5 п.п. при базовой конверсии около 40%, нужно примерно 1500 начатых сессий на вариант.

## События

`POST /api/events` принимает массив до 50 событий:

```json
[{
  "event_id": "uuid",
  "session_id": "uuid",
  "client_timestamp": "2026-01-01T12:00:00Z",
  "type": "step_viewed",
  "step_id": "work_mode",
  "properties": { "step_type": "single", "visible_step_index": 1, "visible_step_count": 7 }
}]
```

Версию, вариант, UTM и серверное время сервер берёт из сессии, клиент их не присылает. В ответе у каждого события свой статус: `accepted`, `duplicate` или `rejected` с причиной. Каждое событие пишется в отдельной транзакции, поэтому одно плохое не ломает пачку. `event_id` — первичный ключ: повтор после таймаута получает `duplicate` и дубля не создаёт.

Типы событий: `session_started`, `step_viewed`, `answer_submitted`, `step_completed`, `back_clicked`, `result_viewed`, `cta_clicked`, в v3 ещё `recommendation_expanded`. Разрешённые события и их свойства берутся из конфига закреплённой версии: v1-сессия не может прислать событие из v3.

`session_started`, `answer_submitted`, `step_completed` и `back_clicked` пишет только сервер в транзакции создания или изменения сессии. Публичный endpoint отклоняет эти типы и прямую отправку производных событий с `emitOn`. Просмотры и клики клиент складывает в `localStorage` (`funnel_event:<id>`) до отправки и повторяет при загрузке, при восстановлении сети и раз в 5 секунд.

**Доверие к событиям.** Сервер сохраняет достигнутые шаги и выданные пары результат/CTA в `step_contexts`. Просмотр принимается только для достигнутого шага, `result_viewed` и `cta_clicked` — только для достигнутого result-шага с выданными этой сессии `result_id` и `action`. Если эти свойства опущены, сервер подставляет значения сохранённого контекста. Контексты сохраняются после Back, смены ветки, перезапуска и отката версии: отложенные события остаются допустимыми. Одной отправкой событий нельзя создать переход или выдать себе результат. Происхождение `server`/`client` проставляет сервер, поле из запроса его не меняет.

**Обновление старой базы.** События, записанные до проверки доверия, сохраняются с происхождением `legacy` и исключаются из метрик. Админка показывает их количество. Задним числом отличить настоящие события от поддельных нельзя; повтор старого `event_id` не делает запись проверенной. Сессии и версии сохраняются: контексты восстанавливаются из текущего состояния и истории переходов на сервере. Прошлые результаты и шаги, уже удалённые из истории до обновления, восстановить достоверно нельзя — такие отложенные события отклоняются.

**Приватность.** Сырые ответы лежат только в `sessions.answers` — они нужны для веток и результата. В события попадают только ID шагов и результатов, тип ответа и счётчики. Неизвестные свойства и вложенные объекты отклоняются.

## Модель данных

| Таблица | Что хранит |
|---|---|
| `configs` | исходный JSON, внутренний номер, время публикации |
| `activations` | журнал активаций для отката |
| `meta` | активная версия |
| `sessions` | версия, вариант, UTM, ответы, история, текущий шаг, время создания |
| `events` | `event_id` (PK), сессия, серверное и клиентское время, тип, версия, вариант, шаг, UTM, свойства, происхождение |
| `step_contexts` | достигнутые шаги и выданные пары результат/CTA; без сырых ответов |

## Как считается аналитика

Все метрики — по уникальным сессиям и проверенным событиям, в разрезе версия × вариант, с фильтром по `utm_campaign`.

- **Начали** — сессии с хотя бы одним проверенным событием, кроме `session_started`. Создание сессии через API без дальнейшей активности не считается. Общее число созданных сессий видно отдельно.
- **Просмотр шага** — у сессии есть `step_viewed` этого шага, сколько бы раз он ни повторялся.
- **Конверсия шага** — доля сессий, увидевших следующий шаг, среди увидевших текущий. Следующий шаг берётся из `step_completed.next_step_id`, поэтому возврат назад со сменой ветки не переписывает прошлые переходы. **Отвал** — остальные.
- **Результат** — есть `result_viewed`.
- **CTR** — сессии с результатом и кликом / сессии с результатом. Клик, пришедший раньше результата, не даёт больше 100%.

Считаются множества, а не суммы, поэтому дубли и порядок прихода событий на результат не влияют.

## Генератор

`npm run generate` создаёт 120 сессий через те же методы, что и живой трафик: 60 A / 60 B, четыре кампании, разные ветки и точки отвала, возвраты, повторные просмотры, дубли `event_id`, повтор целой пачки и события в обратном порядке. На v3 генерирует и `recommendation_expanded`. На чистой базе с v1 получается 120 начатых, 47 результатов, 29 кликов. В конце скрипт сверяет ответы сервера и прирост сессий. На публичный стенд генератор не запускался — там только реальные сессии.

## Как я работал с агентами

Код писал Codex. Моя часть — разбить работу, поставить задачи, проверить результат и принять решения там, где ТЗ допускает варианты.

**Разбивка.** Работа шла в нескольких параллельных сессиях Codex по независимым частям: runtime воронки и состояние сессии, приём событий и аналитика, админка, генератор и тесты. Общие типы лежат в `shared/types.ts` — это контракт между частями.

**Ревью.** Отдельная сессия получила только ТЗ и код и прошла по каждому требованию, воспроизводя проблемы на реальных методах. Что она нашла в почти готовой первой версии:

- возврат назад со сменой ветки переписывал историческую аналитику: просмотр шага пропадал из отчёта;
- новое событие, объявленное в конфиге, отклонялось — вторая итерация бы сломалась;
- временная ошибка сети при загрузке создавала новую сессию вместо старой;
- проверка свойств событий пропускала лишнее, README обещал больше, чем покрыто тестами.

Каждая находка исправлена с регрессионным тестом. Позже было ещё одно ревью другой моделью (Claude Code). Оно нашло логическую ошибку в гипотезе (заголовки результата не могут влиять на достижение результата), завышенное «начали» и откат по номеру вместо истории. Эти ошибки исправлены.

Проверка до сдачи пропустила подделку результата и CTA через публичный endpoint. После обратной связи сценарий воспроизведён, добавлена проверка по серверным контекстам и исключены непроверяемые старые события. Независимое ревью исправления выявило крайние случаи миграции после Back и приём объявленных в конфиге пользовательских событий; для них добавлены регрессии.

**Решения.** Состояние хранится на сервере, а не в браузере. `node:sqlite` без ORM. Сырые ответы не попадают в события. CTR считается только по сессиям с результатом. Изменение долей A/B — это новая версия, а не правка текущей.

## Ограничения и допущения

- Один инстанс: SQLite и счётчики rate limit в памяти.
- Аналитика на каждый запрос читает все события выбранной выборки. На тестовых объёмах это миллисекунды, на миллионах событий нужны предрасчёт или инкрементальные агрегаты.
- Админка на одном токене, без ролей и журнала действий.
- CTA раскрывает план действий на месте, внешнего перехода нет.
- Сессия живёт 72 часа (`ttlHours` из конфига). После этого создаётся новая, старые данные не удаляются.
- Очистка хранилища браузера теряет черновик и неотправленные события.
- Обычные вкладки делят одну сессию, изолированы только проверочные вкладки A/B.
- Проверка контекста подтверждает, что сервер разрешил шаг, результат и CTA. Сам факт просмотра или физического клика остаётся сообщением клиента: автоматизированный клиент, прошедший допустимый путь, неотличим от человека. Это не система антифрода для платного трафика.

## Защита API

- Лимиты в минуту на IP / на инстанс: 300 / 3000 запросов, 20 / 200 новых сессий, 600 / 6000 событий. При превышении — `429` с `Retry-After`, клиентская очередь повторит позже.
- На одну сессию — до 2000 событий. UTM: до 10 полей `utm_*`, до 256 байт на значение.
- ID сессии из URL не принимается.
- `X-Forwarded-For` учитывается только от адресов из `TRUST_PROXY`.
- Токен админки сравнивается за постоянное время.

## Структура

- `shared/` — типы и расчёт интервала A/B
- `server/config.ts`, `server/events.ts` — нормализация и валидация конфигов и событий
- `server/core.ts` — SQLite, сессии, версии, приём событий
- `server/analytics.ts` — агрегация
- `server/app.ts` — HTTP
- `src/` — воронка (`Funnel.tsx`, `useFunnel.ts`), очередь событий (`transport.ts`), админка (`admin/`)
- `docs/verification.md` — что и как проверялось
