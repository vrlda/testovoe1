# Funnel Runtime

Мини-платформа для конфигурируемых воронок: React, TypeScript, Node.js и SQLite. Первая и вторая итерации задания.

- Воронка: https://test.vrld.cc
- Панель управления: https://test.vrld.cc/admin
- Репозиторий: https://github.com/vrlda/testovoe1

Для панели нужен токен администратора, который передаётся проверяющему отдельно.

## Локальный запуск

Нужен Node.js 24+ с `node:sqlite`.

```bash
git clone https://github.com/vrlda/testovoe1.git
cd testovoe1
npm ci
ADMIN_TOKEN=change-this npm run dev
```

Воронка: http://localhost:5173, панель: http://localhost:5173/admin. Backend работает на порту 3001. Для запуска собранного приложения:

```bash
npm run build
ADMIN_TOKEN=long-random-secret PORT=3001 npm start
```

Frontend и API обслуживаются с одного адреса. Без непустого `ADMIN_TOKEN` сервер не запускается. База `data/funnel.sqlite` создаётся автоматически и не попадает в Git. Шрифты включены в сборку; внешние сервисы не используются.

## Конфигурация и состояние

[`configs/workstyle-v1.json`](configs/workstyle-v1.json) и [`configs/workstyle-v2.json`](configs/workstyle-v2.json) — конфиги первой итерации. [`configs/workstyle-v3.json`](configs/workstyle-v3.json) — полученный для второй итерации конфиг. Файлы сохранены без изменений. Новая база автоматически публикует v1; v2 и v3 загружаются через панель без передеплоя. Во всех версиях есть варианты A/B с разным порядком вопросов, текстами и результатами.

Экраны строятся из JSON: single-select, multi-select, числовой ввод, информационный экран и результат с CTA. Backend обрабатывает `visibleWhen`, ограничения ввода и `resultRules`. Например, вопрос об офисных днях доступен только для гибридного и офисного формата; в v3 вопрос о доступе к информации появляется только при выборе compliance. В варианте B v3 отсутствует `tool_count`. Прогресс учитывает доступные вопросы; информационный экран и результат исключены из их количества.

Ответы, текущий шаг и история хранятся на сервере. Черновики ввода сохраняются в браузере по сессии и шагу. Back, refresh и повторное открытие страницы восстанавливают состояние. Временная ошибка соединения сохраняет ID сессии и предлагает повторить запрос.

Интерфейс на английском, как и предоставленный конфиг (`locale: en-AU`). Тексты экранов отображаются прямо из JSON без перевода; идентификаторы и значения ответов сохраняются без изменений.

## Версии и rollback

Во вкладке **Versions** можно загрузить JSON или вставить его содержимое. Сервер проверяет конфигурацию, сохраняет неизменяемую версию и делает её активной без передеплоя. Старые сессии сохраняют прежнюю конфигурацию и вариант; новые создаются на активной версии.

Кнопка отката активирует предыдущую версию. Существующие сессии, события и аналитика сохраняются. Если предыдущей версии нет, кнопка недоступна. Для проверки второй итерации: опубликовать v2, затем v3, пройти новую ветку и вариант B, выполнить rollback и проверить, что новые сессии используют v2, а сессии v3 продолжаются на v3. Это не требует изменения схемы базы.

## A/B-эксперимент

Backend назначает A или B с весами из конфигурации. Вариант закреплён за сессией. Во вкладке **A/B test** доступны распределение трафика, порядок экранов, результаты и сравнение метрик.

Гипотеза: более ранний вопрос о формате работы и другая подача результата в B увеличат долю пользователей, дошедших до рекомендации. Основная метрика: уникальные сессии с `result_viewed` / начатые сессии. Разница между вариантами показана в процентных пунктах; статистическая значимость автоматически не объявляется.

Изменение долей через **Publish allocation** создаёт новую версию. `100/0` и `0/100` направляют новые обычные сессии в один вариант. Кнопки **Open A / Open B** используют query override `/?variant=A&new=1` или `/?variant=B&new=1`. Они создают реальные проверочные сессии с кампанией `ab_manual_check`.

Проверочные вкладки используют `sessionStorage`, чтобы A и B не перезаписывали друг друга. ID сессии из URL не принимается и удаляется из адреса. После обновления защиты старые проверочные A/B-сессии в браузере начинают новую сессию; обычные сессии сохраняются. Последняя сессия каждого варианта также сохраняется в `localStorage` для повторного открытия.

## Модель данных и события

SQLite содержит четыре таблицы:

- `configs` — исходный JSON, внутренний номер версии и время публикации;
- `meta` — активная версия;
- `sessions` — закреплённые версия и вариант, UTM, ответы, история, текущий шаг и время создания;
- `events` — события с уникальным `event_id`, ID сессии, серверным и клиентским временем, версией, вариантом, шагом, UTM и свойствами.

`POST /api/events` принимает пачку:

```json
[{"event_id":"uuid","session_id":"uuid","client_timestamp":"2026-01-01T12:00:00Z","type":"step_viewed","step_id":"work_mode","properties":{"step_type":"single"}}]
```

Поддерживаются `session_started`, `step_viewed`, `answer_submitted`, `step_completed`, `back_clicked`, `result_viewed`, `cta_clicked`. В v3 добавляется `recommendation_expanded` с `result_id`, `action` и фиксированным `source: result_cta`; оно отправляется при раскрытии рекомендаций. Сервер добавляет закреплённые версию, вариант и UTM из сессии. Каждый элемент получает статус `accepted`, `duplicate` или `rejected`; ошибка одного не блокирует остальные. Повторный `event_id` не создаёт дубль, включая повтор после timeout.

Создание сессии, ответы, завершение шага и Back записываются вместе с изменением состояния в транзакции. `step_completed.next_step_id` сохраняет фактический переход. Просмотры и CTA попадают в браузерную очередь до отправки; повторы выполняются при загрузке, восстановлении соединения и каждые пять секунд. Пачка содержит до 50 событий. Очередь хранит отдельный ключ `funnel_event:<event_id>` на событие; отклонённые записи сохраняются отдельно для диагностики.

Сырые ответы нужны только для состояния сессии и выбора результата. Свойства событий ограничены безопасными метаданными: типом ответа, ID шага или результата, действием и счётчиками. Произвольные ответы, неизвестные свойства и вложенные объекты отклоняются.

## Аналитика

Dashboard показывает старты, достижение результата, конверсию между шагами, отвал, клики и CTR кнопки. Есть сравнение версий и вариантов и фильтр `utm_campaign`.

Все показатели считаются по уникальным сессиям. Повторные просмотры, Back, дубли и порядок поступления событий не увеличивают счётчики. Конверсия шага — доля сессий, увидевших фактический следующий шаг, среди увидевших текущий; отвал — разница. Исторические просмотры сохраняются после изменения ответа. Для старых событий без записанного перехода используются возможные соседние шаги неизменяемого конфига.

CTR — сессии одновременно с результатом и кликом / сессии с результатом. Поэтому задержанное событие результата не повышает CTR выше 100%. Количество сессий с кликом также показывается отдельно.

## Генератор и проверки

```bash
npm run generate
npm test
npm run build
npm run format:check
```

Генератор запускается только вручную. Он создаёт 120 сессий на активной версии: 60 A / 60 B, по 15 каждого варианта в четырёх кампаниях. Включены разные ветки, точки отвала, возвраты, повторные просмотры, дубли ID, повтор пачки и обратный порядок событий. На v3 он также создаёт `recommendation_expanded`. Команда проверяет ответы приёма и прирост сессий. Для отдельной базы:

```bash
DB_PATH=/tmp/funnel-demo.sqlite npm run generate
DB_PATH=/tmp/funnel-demo.sqlite ADMIN_TOKEN=change-this npm start
```

Для исходного конфига свежий прогон даёт 120 сессий, 47 результатов и 29 сессий с кликом. Синтетические данные не доказывают гипотезу A/B. На публичном сайте генератор заранее не запускается.

Автоматические тесты проверяют закрепление версии и варианта, публикацию/откат, дедупликацию, аналитику после смены ветки, валидацию, HTTP-контракты, истечение сессии и повторную доставку событий. Результаты проверки — в [docs/verification.md](docs/verification.md).

## Структура

- `shared/types.ts` — общие типы конфигурации и API;
- `server/config.ts`, `server/events.ts` — нормализация и валидация;
- `server/core.ts` — SQLite и переходы состояния;
- `server/analytics.ts` — агрегация; `server/app.ts` — HTTP;
- `src/Funnel.tsx`, `src/useFunnel.ts` — экран и жизненный цикл сессии;
- `src/admin/` — аналитика, A/B и публикация;
- `src/transport.ts` — HTTP и сохраняемая очередь.

Подготовленные SQL-запросы и неизменяемые конфиги кешируются. Аналитика не загружает сырые ответы и не выполняет запрос на каждую сессию. TypeScript проверяет неиспользуемые переменные; `npm run format` форматирует исходники, не затрагивая исходный JSON.

## Ход работы и ограничения

Первая итерация: v1 и v2, runtime, состояние сессий, события, dashboard, генератор, управление A/B и проверки повторной доставки. Вторая итерация: получен v3, добавлены оператор `contains` для условной ветки, поддержка нового события и проверка удалённого шага в B. После публикации v3 выполнен rollback без изменения схемы базы и потери аналитики. Интерфейс показывает исходный английский контент конфигов. Проверка включает чистую установку, автоматические тесты, SQL-сверку метрик и браузерные сценарии.

CTA раскрывает локальный план действий. Панель использует общий токен без ролей и журнала административных действий. SQLite рассчитана на один экземпляр сервера. Обычные вкладки браузера разделяют текущую сессию; проверочные A/B-вкладки изолированы.

Срок сессии в исходном конфиге — 72 часа. Подтверждённый 404 или истечение срока создаёт новую сессию; временная ошибка — нет. Исторические данные не удаляются. Очистка браузерного хранилища удаляет локальные черновики и неотправленные события.

## Защита API

UTM: до 10 полей с именами `utm_*` (латинские строчные буквы, цифры и подчёркивание), до 256 байт на значение и 2048 байт на объект. Сервер принимает до 50 событий за запрос и до 2000 уникальных событий на сессию; повтор уже принятого ID не расходует лимит. Старые записи с недопустимыми UTM сохраняются, но новые события для них отклоняются.

Лимиты за минуту на IP / весь экземпляр: 300 / 3000 запросов API, 20 / 200 новых сессий, 600 / 6000 входящих событий. При превышении сервер возвращает `429` с `Retry-After`; очередь сохраняет события для повторной отправки. Счётчики запросов хранятся в памяти одного экземпляра, лимит событий сессии — в SQLite.

По умолчанию заголовки прокси не влияют на IP клиента. За обратным прокси задайте `TRUST_PROXY` только точными адресами доверенных прокси через запятую и закройте прямой доступ к backend. Прокси должен перезаписывать входящий `X-Forwarded-For`. Не задавайте доверие ко всем адресам.
